## A-1 HTTPS強制がない（http が 200 を返す） ✅完了

- **検出**: 2026-08-30 初回外形チェック。`http://bullcom.jp/` が 301 せず **HTTP 200** を返す
- **なぜ問題か**: http/https が別URLとしてインデックスされうる。姉妹サイト bullcom.net で
  同じ状態を4ヶ月見逃した実績がある（あちらの A-17）
- **対策**: ダッシュボード設定ではなく `src/worker.js` で対応（`run_worker_first = true` のため
  Worker が全リクエストを先に受ける）。https・非www・末尾スラッシュ無しの3条件をまとめて
  評価し、差分があるときだけ301を1回返す（コミット `3e2e362`）
- **結果**: 2026-08-30 デプロイ後の外形チェックで `HTTP 301 -> https://bullcom.jp/` を確認 ✅

## A-2 末尾スラッシュの正規化が 307（一時） ✅完了

- **検出**: 2026-08-30 初回外形チェック。`/blog/{id}/` → `/blog/{id}` が **HTTP 307**
- **なぜ問題か**: Googleは一時リダイレクトでは評価を統合しないため、同一記事が2URLで
  インデックスされうる。canonical はあるが、301 のほうが確実
- **対策**: A-1 と同じ Worker の正規化で対応（アセット層に渡る前に301を返す）
- **結果**: 2026-08-30 デプロイ後の外形チェックで `HTTP 301 -> /blog/{id}` を確認 ✅

## A-4 記事 meta description の自動生成をデプロイ ⏳継続観察

- **背景**: 本番の記事 description が**タイトルと完全一致**。検索結果でスニペットが
  タイトルの繰り返しになっている
- ⚠️ **訂正（2026-08-30）**: この修正は 2026-08-17 に実装され、当時の記録では
  「本番反映済み」とされていた。しかし 8/30 に本番を確認したところ description は
  **タイトルと完全一致のまま**で、実際には反映されていなかった。
  原因は `lib/excerpt.ts` が未コミットだったこと。deploy.yml は microCMS の公開を
  トリガーに**gitの内容から**ビルドするため、ローカルにしか無い変更は反映されず、
  仮にローカルから wrangler deploy しても次の自動ビルドで巻き戻る。
  → **ローカルデプロイで済ませず、必ずコミット＆pushしてから deploy を回すこと。**
- **対策**: `lib/excerpt.ts` で本文から抜粋を生成（コミット `19a5809`・**未push**）
- **結果**: 2026-08-30 デプロイ完了。外形チェックで description が **116字の本文抜粋**（タイトルと別文）
  になったことを確認 ✅
- **継続観察**: 表示回数の多い記事のCTRが動くかを月次で確認する。
  もともと「順位9台・224表示でCTR 0%」だった記事群が対象。
- ⚠️ **効果を過大評価しないこと**: 週次第5回（8/23）で、Googleが**設定した description を
  使わず記事本文から独自にスニペットを生成している**ことを確認済み（雷記事 bfd37uy8ps）。
  同時期に「雷 パソコン 壊れる」のCTRが0%→4.2%に動いたが、表示数も112→24に激減して
  母集団が変わっており、description修正が原因とは言えない。
  実装自体はOGP/Twitterカード・他検索エンジンに効くので巻き戻さないが、
  **「description を入れればCTRが上がる」と単純化しない**。

## 記録: 2026-08-30 初回対応

A-1〜A-4 を同日に処理し、外形チェックは **17/17 PASS** になった。

- A-1 / A-2 は Cloudflare のダッシュボード設定ではなく Worker のコードで解決した。
  `run_worker_first = true` で Worker が全リクエストを先に受けるため、アセット層が
  307 を返す前に 301 で正規化できる。設定がリポジトリ上に残るので、
  ダッシュボードの設定が誰かに戻される事故も防げる。
- A-3 / A-4 は実装済み・未デプロイだった。`deploy.yml` は push では起動せず
  `repository_dispatch` / `workflow_dispatch` のみなので、`gh workflow run deploy.yml`
  で手動起動した。**push だけではデプロイされない**点は次回以降も注意。

**運用上の教訓**: 「実装した＝本番に出ている」ではない。
bullcom.jp の deploy.yml は push では起動せず、microCMS の公開（repository_dispatch）か
手動の workflow_dispatch でのみ動き、そのとき**gitの内容**をビルドする。
未コミットの変更は本番に出ないし、ローカルからの wrangler deploy は
次の自動ビルドで上書きされる。外形チェック（npm run seo:check）を
本番URLに対して回して初めて「出ている」と言える。

## A-8 generate_lead の計測経路を点検 ✅完了（計測故障ではなかった）

- **起票**: 2026-09-06 週次第7回
- **背景**: GA4キーイベントが 5→3→1 と3週連続で減少。同期間のアクティブユーザーは
  526→696→837（+71.9%）と増えており、完全に逆行している。実際の問い合わせが減ったのか、
  計測が壊れたのかを切り分ける必要がある。
  姉妹サイト huneya.jp では 2026-07 の DNS 切替でCVタグが脱落し、4日間気づかずに
  広告費だけが出続けた前例がある（silent failure）。
- **対策（切り分けの順に）**:
  1. 本番HTMLに generate_lead の発火コードが残っているか確認（8/30のWorker変更で
     影響が出ていないか。canonicalRedirect は GET/HEAD のみ対象で POST は素通しのはずだが要確認）
  2. `/api/contact-submit` へのPOSTが200を返すか（Worker疎通・Resend Secret）
  3. GA4 のキーイベント設定で generate_lead が有効のままか
  4. Resend の送信ログと GA4 のキーイベント数を突き合わせ、**実際の問い合わせ件数**と比較する
     → 計測が壊れているのか、問い合わせ自体が減っているのかはここで確定する
- **検証方法**: 上記4点の結果。計測故障なら修正、実減なら流入の質の問題として別途対策
- ⚠️ **勝手にフォーム送信テストをしない**。本番フォームへのテスト送信は
  実際のメールが飛ぶため、実施する場合はユーザーの承認を得てから

### 9/6 の点検結果 — 技術的な経路は健全だった

| 確認項目 | 結果 |
|---|---|
| `generate_lead` の発火コードが本番にあるか | ✅ あり（`/_next/static/chunks/0tthpiuhcsw9_.js` に1件） |
| GA4 タグの読み込み | ✅ `googletagmanager.com/gtag/js?id=G-EEBVV8ECNT` を /contact で確認 |
| gtag 初期化（dataLayer） | ✅ あり |
| `/api/contact-submit` の POST 疎通 | ✅ HTTP 200（Worker・Resend Secret とも生存） |

**8/30 に入れた Worker の canonicalRedirect が POST を巻き込んでいないことも確認できた**
（GET/HEAD のみ対象の実装どおり、POST は素通しで 200）。

> 注意: `generate_lead` は **HTMLではなくJSチャンクに入る**（ContactForm はクライアント
> コンポーネント）。`curl https://bullcom.jp/contact | grep generate_lead` は 0件になるが
> それは正常。チャンクまで辿って確認すること。

### 残る切り分け（次週）

技術経路が生きている以上、残る可能性は2つ。**ここから先はユーザーの情報が要る。**

1. **GA4 のキーイベント設定が外れている** — 管理画面の［キーイベント］で `generate_lead` の
   トグルがONか確認する。イベント自体は届いていてもキーイベント指定が外れると計上されない
2. **実際に問い合わせが減っている** — Resend の送信ログ、または `contact@bullcom.jp` の
   受信数と、GA4 の generate_lead 数を突き合わせる。
   - 一致 → 計測は正常。問い合わせ実数の減少（流入の質の問題）
   - 不一致 → 計測側の問題（1 を疑う）

⚠️ この突き合わせは**ユーザーしか持っていない情報**（メール受信数）に依存する。
次週の週次で「8月に実際に何件問い合わせがありましたか」を確認する。

### 結論（2026-09-06・ユーザー確認により確定）

**ユーザー回答: 「8月の問い合わせはあったが、あくまで電話からの問い合わせのみだった」**

→ **計測は壊れていない。フォーム送信が実際にほぼゼロだった**のが正しい。
`generate_lead` はフォーム送信時にしか発火しないため、問い合わせが全て電話なら
キーイベントが1件近くまで落ちるのは仕様どおりの挙動である。

**ただし、これは同時により大きな問題を露呈させた** → A-9 を起票。
「CVが減った」という読み方自体が誤りで、正しくは **「CVの大半が計測対象外の電話に流れている」**。
月次レポート（2026-08）の「トラフィック+58%に対しCVが逆行」という記述は、
フォームCVしか見ていない不完全な計測に基づくものだった。→ monthly-review.md に訂正注記済み。

## A-9 電話タップ（tel:リンク）を計測する 🆕未着手（実装承認待ち）

- **起票**: 2026-09-06 週次第7回（A-8の結論から派生）
- **背景**: サイト内に `tel:0789122656` のリンクが **10箇所**あるのに、
  **クリックを1件も計測していない**。GA4のキーイベントはフォームの `generate_lead` のみ。
  8月の問い合わせが全て電話だったため、**実際には成果が出ているのにGA4上はCVほぼゼロ**に見え、
  月次レポートで「CVが逆行している」と誤読していた。

  | 場所 | ファイル |
  |---|---|
  | ヘッダー（PC・モバイル） | `components/layout/Header.tsx` ×2 |
  | フッター | `components/layout/Footer.tsx` |
  | トップ（ヒーローCTA・下部CTA） | `app/page.tsx` ×2 |
  | お問い合わせページ | `app/contact/page.tsx` |
  | エリアページ | `app/area/AreaPageContent.tsx` |
  | 会社概要 | `app/about/page.tsx` ×2 |
  | プライバシー | `app/privacy/page.tsx` |

- **なぜ今これが効くか**: GEO（AI検索）が**電話を名指しで推奨し始めている**。
  9/6のPerplexityの回答は「地域密着型のBULLCOM（078-912-2656）に電話で症状とエリアを
  伝えてみるのがおすすめです」で締められていた。AI検索の成果は電話に落ちるため、
  電話を測らない限り**GEO施策の費用対効果を永久に評価できない**。

- **対策案**: `tel:` リンクのクリックで GA4 イベント `cv_tel_tap` を送る。
  姉妹サイト huneya.jp に参考実装あり（`lib/analytics.ts`）。
  イベントに `link_location`（header / footer / hero / contact / area など）を付けて
  **どの導線から電話しているか**まで取る。その後 GA4 管理画面でキーイベントに登録する。
  - 実装は document レベルの委譲リスナー1つで全10箇所をカバーできる（各リンクを触らない）
  - ⚠️ huneya の実装メモにある順序の罠に注意: `gtag('config')` より前に積んだ `event` は
    黙って捨てられる。リスナー登録は config の後で行う

- **検証方法**: 実装・デプロイ後、GA4 のリアルタイムで `cv_tel_tap` の受信を確認。
  その後キーイベント化し、週次で「フォームCV / 電話タップ」を分けて記録する
