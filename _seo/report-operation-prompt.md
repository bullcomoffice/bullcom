# 他セッションへ運用変更を反映するためのプロンプト

週報・月報の運用（日曜週報＋最終日曜月報）を他プロジェクトのセッションへ持ち込むための、
**そのまま貼り付けられるプロンプト**。ルールの本文は [`report-operation.md`](./report-operation.md)。

---

## 1. 既存タスクの運用を変更するとき

> 対象プロジェクトのセッション（bullcom.net、huneya.jp など）で使う。

```
週報・月報の運用を変更します。以下のルールに合わせて、このプロジェクトの
スケジュールタスクを更新してください。

## 新しい運用
- 週報: 毎週【日曜】（変更前は月曜など）
- 月報: 毎月【最終日曜】（変更前は毎月1日）
- 最終日曜は週報を実施せず、月報が週報を兼ねる

## なぜ変えるか
- 日曜にすると対象期間が週の区切り（日〜土）と一致する。月曜実施では
  「先週月〜日」を見る形でGSCの週次バケットと1日ずれていた。
- 月報を最終日曜に固定すると、日曜1本で運用が閉じる。「毎月1日」は曜日が
  毎月動くため、週報と重なる週・空く週が生じていた。

## 実装方法（重要）
cron は「第N曜日」を表現できません。`0 9 22-28 * 0` のような書き方は、
曜日と日付をAND/ORのどちらで評価するかが cron 実装によって変わるため使わないこと。

**週報・月報とも毎週日曜起動（`分 時 * * 0`）にして、プロンプト冒頭で
「今日が当月最後の日曜か」を判定し、自分の担当日かを決める**方式にしてください。

判定式:
    if [ "$(date -d '+7 days' +%m)" != "$(date +%m)" ]; then echo last-sunday; else echo normal-sunday; fi

週報タスクのプロンプト冒頭に入れる文:
    まず今日が当月最後の日曜かを判定する。
      if [ "$(date -d '+7 days' +%m)" != "$(date +%m)" ]; then echo last-sunday; else echo normal-sunday; fi
    last-sunday なら「本日は月次レビュー日のため週次レポートはスキップします」と
    一行だけ返して終了する。normal-sunday のときだけ以下を実行する。

月報タスクのプロンプト冒頭に入れる文:
    まず今日が当月最後の日曜かを判定する。
      if [ "$(date -d '+7 days' +%m)" != "$(date +%m)" ]; then echo last-sunday; else echo normal-sunday; fi
    normal-sunday なら「本日は月次レビュー日ではありません」と一行だけ返して終了する。
    last-sunday のときだけ以下を実行する。
    なお本日は週次レポートを実施しないため、週次の必須項目（外形チェック・前週対策の
    答え合わせ・当週データ・週次ログへの記録）も本レビューに含めること。

## 守ること
- 既存プロンプトの中身（対象KW・記録先ファイル・GSCプロパティ・承認ルール）は変えない。
  スケジュールとガード文の追加だけを行う。
- 実施時刻は他プロジェクトのレポートと重ならないようにする
  （bullcom.net 9:00 ／ huneya 10:23 ／ bullcom.jp 11:00 が使用中）。
- 変更したら、判定式を実際の日付で走らせて、今後5〜6回の日曜が週報／月報の
  どちらになるかを一覧で示して確認すること。
```

## 2. 週報・月報を新規に作るとき

> まだ週報・月報が無いプロジェクトで使う。

```
このプロジェクトにSEO/GEOの週報・月報の運用を新設してください。
ルールは D:\Data\Projects\Next\bullcom\_seo\report-operation.md に従います
（実装済みの参考例が同ディレクトリの _seo/ 一式）。

## スケジュール
- 週報: 毎週日曜（最終日曜はスキップ）／15分
- 月報: 毎月最終日曜のみ／1時間。週報を兼ねる
- 起動はどちらも `分 時 * * 0`。担当日かの判定はプロンプト冒頭のガード式で行う
  （cron は第N曜日を表現できないため）
- 実施時刻は他プロジェクトと重ねない（bullcom.net 9:00 ／ huneya 10:23 ／ bullcom.jp 11:00）

## 週報の中身（15分）
1. 外形ヘルスチェック — 退行があればそれを最優先の問題点にする
2. 答え合わせ — 対策台帳の「🔵検証中」「⏳継続観察」を今週データで検証しステータス更新
3. データ収集（過去7日 = 前週日〜土）
   GSC（表示/クリック/CTR/平均順位・主軸KW別）／GA4（セッション・直帰率・新規記事PV）／
   新記事の索引状況／GBP（表示・電話タップ・経路検索）／GEO引用テスト（ChatGPT・Claude・Perplexity ○×）
4. 問題点抽出 — 1〜3個に絞って言語化
5. 対策立案 — 承認されたものを対策台帳にA-番号で採番
6. 記録 — 週次ログに追記、git commit & push

週報でやらないこと（月報に回す）:
個別KWの順位精査／推移のグラフ化／リライト候補の選定／記事テーマ決定

## 月報の中身（1時間）
対象期間は前回月報の翌日〜実施日前日（週次ログ4〜5週分）。

0. 週次分の引き継ぎ（必須。省くとその週の答え合わせが抜け落ちる）
   外形チェック／答え合わせ／当週データの取得と週次ログへの記録
1. 週次データ4〜5週分の推移をグラフ化（表示/クリック/CTR/順位）
2. 主軸KWの平均掲載順位推移＋**選定時に無かった新規クエリの台頭**を確認しKWを見直す
3. コンバージョン（GA4のフォーム送信数）
4. GEO引用率の月間集計（週次○×の集計）
5. インデックス健全性（登録済み数・重複/正規未選択の減少・URL検査・サイトマップ・構造化データのエラー）
6. リライト候補選定（表示回数多×順位低）
7. 翌月の記事テーマ3〜5本決定
8. 記録 — 月次チェックリストの「記録」欄に追記、commit & push

## 作るもの
- _seo/README.md（サイト固有の前提・対象KW・実務メモ）
- _seo/weekly-log.md（テンプレ付き・最新を上に追記）
- _seo/monthly-review.md（チェックリスト兼記録先）
- _seo/action-log.md（対策台帳。🔵検証中 / ⏳継続観察 / ✅完了 / ❌棄却）
- _seo/health-log.md（外形チェック履歴。スクリプトが --append で追記）
- scripts/seo-healthcheck.mjs（依存なし・Node18+ の fetch のみ。npm run seo:check / seo:log）

## 外形チェックで見る項目
トップ200／www→非www 301／http→https 301／末尾スラッシュの301正規化／canonical／
sitemap.xml（URL数・末尾スラッシュ混入）／robots.txt（AIボット許可・Sitemap行）／llms.txt／
LocalBusiness／FAQPage／記事の構造化データ／記事descriptionがタイトルと別文であること

⚠️ サイトごとに**正規形が違う**。末尾スラッシュの有無は必ず対象サイトの実装を確認してから
判定を書くこと（bullcom.jp は末尾スラッシュ無し、bullcom.net は有り）。

⚠️ description の判定でtitleからサイト名を取り除くとき、**先頭の区切り文字で分割しない**こと。
記事タイトル自体に区切り文字が含まれると前半だけを拾い、同一なのにPASSする。
サイト名サフィックスを末尾から除去して比較する。

## 最後に
作成後、外形チェックを1回実行して現状を把握し、失敗項目があれば対策台帳に
A-番号で起票してから報告してください。
```
